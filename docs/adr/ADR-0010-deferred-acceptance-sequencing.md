# ADR-0010：延期统一验收下的阶段推进与状态审计

- 状态：Accepted by project owner
- 日期：2026-09-01

## 背景

总任务书要求当前阶段通过后才能进入下一阶段，并要求每阶段生成 `ACCEPTANCE.md`。项目业主
随后明确要求先完成所有阶段实现，再统一执行正式验收。继续实施与“不伪造阶段通过”必须同时
满足，不能把测试通过偷换为 `accepted`，也不能倒填验收时间。

## 决定

1. 阶段实现、验证与正式验收分离。实现和规定测试完成后可记录
   `implementation_verified_acceptance_deferred`，但该状态不等于任务书的 `accepted`。
2. `PROJECT_PHASE_STATE.yaml` 的顶层 `current_phase` 指向当前正在实施的阶段，状态只能使用
   任务书允许的 `in_progress`；此前已验证但尚未正式验收的阶段进入
   `deferred_acceptance_queue`，保留实现提交、证据提交与工件清单哈希。
3. 延期阶段不生成 `ACCEPTANCE.md`，`accepted_at_utc` 和权威 `commit_sha` 保持空值。阶段报告
   必须明确写出“实现验证完成、正式验收延期”。
4. 此决定只改变验收时点，不降低阶段依赖的技术、安全和正确性门禁。后续阶段只能在前一阶段
   完整实现、完整测试、证据清单可验证且无阻断问题时开始。
5. 全部实现完成后，项目业主明确发起统一验收；届时按顺序重新运行各阶段仍适用的门禁、生成
   缺失的 `ACCEPTANCE.md`，并写入真实验收时间与提交绑定。禁止批量伪造历史通过记录。
6. 任一延期阶段出现失败、阻断、安全回归或证据失效，立即停止推进并把当前阶段标记为
   `failed` 或 `blocked`。

## 后果

- P05 保持未验收，进入延期验收队列；P06 可以在完整继承 P05 会计与安全门禁的前提下实施。
- 阶段状态不再暗示“离开即验收”，审计方可区分实现提交、证据提交和正式验收提交。
- 这是项目业主对执行顺序的显式治理决定，不是对 `LIVE_TRADING`、账本、对账或测试要求的豁免。
